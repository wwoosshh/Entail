# entail 의미 보존 외부 GPU 시험 규약

2026년 10월 1일 제안. 이 문서는 실제 GPU 측정 결과가 아니다. 외부 세션은 설계안의 블록 FP8 보호 범위를 구현하고, 아래 조건을 시험 시작 전에 고정한다. 구현과 판정 기준을 holdout 결과에 맞춰 수정하면 새로운 판의 시험으로 분리한다.

## 판정할 명제

고정한 환경과 지원 입력 범위에서, 올바른 생산자의 FP8 값·스케일·배치 의미를 소비하는 보호 호출은 뜻과 수치 허용치를 만족하는 전체 결과를 다음 연산에 전달하거나, 결과를 전달하기 전에 명시적으로 거부한다.

결과를 전달한 경우의 정확성과 정상 입력에서 결과를 얻을 수 있는 사용 가능성을 함께 평가한다. 모델 문장의 자연스러움은 이 명제의 oracle로 사용하지 않는다.

## 환경 조사와 동결

GPU, VRAM, compute capability, driver, OS, Python, torch, CUDA, Triton, vLLM, 설치 wheel의 hash와 commit, precision 설정을 기록한다. entail 2.1.4 d0769c6을 비교 기준으로 둔다. 더 최신 기준을 쓰면 차이와 이유를 동결 전에 기록한다. 연구 기준은 1c24387이다.

먼저 기존 GPU 환경에서 작은 함수 실행을 확인한다. FP8 경로가 이 장치에서 실제로 선택되는지 검사한다. 다른 커널을 실행한 채 FP8 경계 시험을 통과했다고 보고하지 않는다. 새 다운로드가 필요하면 파일·revision·용량을 기록하고 작은 함수 시험부터 수행한다.

과거 실엔진 측정은 Marlin·Humming을 끈 Triton 경로에 도달했다. 당시 설정은 VLLM_DISABLED_KERNELS=MarlinFP8ScaledMMLinearKernel,HummingFP8ScaledMMLinearKernel이었다. 외부 세션은 동결한 엔진 소스에서 이 설정의 유효성을 확인하고 실제 dispatch를 기록한다. 대상 소비 함수에 닿았다는 기록만으로는 부족하다. 활성값 quantizer의 반환과 가중치 적재·패킹에서 생성한 pair와 epoch가 소비 호출까지 이어졌음을 모든 보호 layer에서 확인한다. 현재 자료에는 producer Layout unknown과 quantizer 미도달이 남아 있어 정확한 생산 hook은 선행 구현 작업이다. [과거 도달 결과](https://github.com/wwoosshh/entail-research/blob/1c24387/lowlevel/l2/RESULTS.md#L261)

환경 조사 후 지원 dtype, 블록 크기, shape·stride 집합, 의미 계약, 오차식, oracle, 정상 calibration 입력, 개발 사례, holdout 생성 규칙, 시간·메모리 예산, 실제 엔진 smoke 입력을 freeze manifest에 저장하고 hash를 남긴다. 결과를 본 뒤 분모에서 사례를 삭제하지 않는다.

## 비교할 실행

각 정상 사례는 fresh process의 off A, off B, 현재 load, 새 보증 프로파일로 비교한다. off A와 off B부터 불안정하면 사전 동등성 기준으로 판정하거나 판정 불가로 남긴다.

각 결함 사례는 결함 있음 off, 결함 있음 현재 load, 결함 있음 새 보증 프로파일을 수행한다. 현재 load에서 broken을 기록하고 오답을 전달하면 실패로 기록한다. 새 프로파일의 엄격 차단은 교정 성공과 구분한다. 현재 모드에 임의 stop 옵션을 더한 결과를 기본 load의 성과로 제시하지 않는다.

## 독립 참조와 허용치

시험 oracle은 entail의 연산 정의, 엔진의 forward_native, 기존 연구 비교 함수를 호출하지 않는 독립 구현으로 만든다. 같은 FP8 저장값을 CPU float64로 해석하고 생산자가 정한 블록 스케일을 적용한 전체 행렬곱을 계산한다. 입력은 작은 행렬부터 시작하므로 큰 모델 없이 가능하다. FP8 변환과 스케일 대응도 별도의 단순 사례로 확인한다.

정확 비교가 가능한 작은 2의 거듭제곱 계열 값을 포함한다. 일반 입력의 오차식은 정상 calibration과 출력 dtype·누산 오차에 근거해 동결한다. NaN/Inf 정책과 허용 입력 범위를 함께 고정한다. 허용치를 넘기지 않는 변이는 유효 결함으로 세지 않고 그 사실을 원자료에 남긴다.

평가 oracle은 항상 전체 출력을 비교한다. 보증 프로파일의 실행 중 검사도 매 실제 호출의 전체 결과를 확인하거나 전체 참조로 계산해야 한다. 일부 행만 확인하는 빠른 실행은 별도의 표본 점검 모드이며 보증 gate의 합격 대상이 아니다. 첫 64행의 일치만으로 나머지 행을 통과시키지 않는다.

## 첫 시나리오 묶음

| 묶음 | 수 | 요구 조건 |
|---|---:|---|
| 정상 | 8 | 작은·큰 배치, 서로 다른 입력 분포, cold·warm, 합법적인 새 스케일·가중치, 지원 stride, 반복 실행과 지원된 graph 경로 |
| 소비 과정 결함 | 12 | 소비 변이 4종과 발생 시점 3종 |
| admission과 미지원 | 4 | 선언 누락, 필수 hook 누락, 지원 밖 옵션, 검사 예외 또는 예산 초과 |

정상 8개와 admission 4개의 정확한 입력·절차를 환경 조사 뒤 동결한다. graph가 첫 프로파일의 지원 밖이면 정상 graph 대신 명시적 거부 사례로 이동하고, 정상 8개는 지원 범위 안에서 유지한다. 이 변경은 결과를 보기 전에 기록한다. graph 지원 자체는 별도 결과로 남긴다.

소비 변이는 블록 스케일 간격 오류, 이웃 블록 스케일 읽기, 다른 가중치의 캐시된 스케일 재사용, 비교 조각 밖 행에서만 잘못 읽기의 네 부류다. 올바른 생산자의 값과 선언은 보존하고 소비·전달·재사용 과정만 변이한다. 생산자에 잘못된 선언을 써 넣고 이를 잡았다는 결과는 별도 무효 입력 시험이다.

발생 시점은 첫 호출, 정상 첫 호출 뒤 새 배치·입력에서 발생, 정상 워밍업·캡처 뒤 replay에서 발생의 세 가지다. graph 변이는 Python 함수를 캡처 뒤 교체하는 것으로 흉내 내지 않는다. 캡처에 들어갈 소비 경로에 동적인 장치 입력 또는 실제 artifact 상태를 사용해 replay에서 변이가 활성화됨을 off 실행으로 입증한다. 이 조건을 구성하지 못하면 미검증으로 남긴다.

정상 첫 16행 이후 256행에서만 틀리는 경우, 첫 64행 밖에만 결함이 있는 경우, shape는 같지만 스케일·가중치의 소유자나 epoch가 달라지는 경우가 반드시 포함돼야 한다. 구현자가 사용한 개발 seed와 다른 holdout seed를 동결 후 평가자가 생성하고 hash를 남긴다. 별도 평가자가 없으면 개발과 분리한 seed·변이 묶음으로 실행하되 눈가림 시험이라고 부르지 않는다.

이 holdout은 공개한 네 변이 부류 안에서 새로운 입력·시점을 검증하는 시험이다. 처음 보는 실제 버그 유형의 검출률로 부르지 않는다. 다음 단계의 실제 신규 버그 재현은 별도 동결판과 미리 읽지 않은 표본으로 측정한다. 본 시험의 유한한 사례를 모두 통과해도 그 재현 실험을 대신하지 않는다.

## 출력 이전 개입의 관찰

시험자가 별도로 둔 다음 연산 관찰자가 전체 반환 텐서와 전달 횟수, 호출 순서를 저장한다. 로그의 resolved가 아니라 실제로 관찰된 결과로 판정한다. graph에서는 캡처된 같은 실행 안의 첫 downstream consumer가 실제로 읽은 값의 snapshot이나 충분한 전체 비교 증거를 보존한다. replay가 끝난 뒤 호스트 반환값만 고쳐 관찰한 것은 이미 graph 안에서 소비된 오답을 막은 것으로 세지 않는다. 이를 예방할 gate가 없으면 연산과 downstream을 별도 실행으로 나누고 검증 후 연결하거나 해당 graph 경로를 거부한다.

- 정상 전달: 전체 결과가 oracle의 허용치 안에 있고 불필요한 교정이 없다.
- 교정 전달: off에서 유효했던 결함을 수정해 같은 실제 호출부터 올바른 전체 결과가 전달된다.
- 명시적 차단: 결과가 전달되기 전에 계약 오류로 종료되며 관련 경계가 식별된다.
- 오답 유출: 틀린 결과가 한 번이라도 전달된다. 사후 발견은 이 결과를 바꾸지 않는다.
- 미검증: hook 미도달, 필요한 경로 미실행, oracle 실패, 산출물 누락 등이다.
- 실행 오류: crash, timeout, OOM 등이다. 차단 성공으로 세지 않는다.

변이를 넣었어도 전체 출력이 정상인 off 사례는 mutation effective가 아니다. 수치 확인을 생략하고 unknown을 반환한 뒤 엔진이 계속 결과를 전달하면 보증 실패다. 같은 호출, 두 번째·세 번째 호출, 반복 replay의 전달을 모두 기록한다.

계획한 결함 12개 각각에서 허용치를 넘는 off baseline을 확보해야 전체 결함 gate를 완료할 수 있다. ineffective 사례를 원자료에 남기되 그 사례를 삭제해서 전체 시험을 passed로 만들지 않는다. baseline을 구성하지 못한 시나리오는 incomplete이며 유효 결함이 0개인 실행은 passed가 될 수 없다. 시험 기준 변경이 필요하면 새 freeze manifest와 별도 시험으로 기록한다.

off는 결함 소비 경로가 실제 실행됐음을 증명한다. on이 dispatch 전에 안전 경로로 바꾸거나 차단했다면 원래 결함 커널이 실행되지 않은 것이 정상이다. 원래 커널 실행 횟수와 안전 경로 실행 횟수를 구분하고, 시험을 위해 on에서도 결함 커널을 억지로 실행시키지 않는다.

## 실제 엔진의 연결 확인

함수 시험 뒤 FP8 모델 한 개에서 실제 quantizer 또는 파일 선언의 producer와 소비 커널 모두에 도달했음을 확인한다. 단순 테스트 함수의 성공과 실엔진의 성공은 별도 표로 보고한다. 장치가 다른 backend를 선택하면 함수 시험만 완료한 것으로 남긴다.

greedy 반복, 명시 seed가 있는 샘플링, seed가 생략된 샘플링, cold·warm cache, 새 요청·배치, 지원 graph replay를 작은 입력으로 비교한다. 실제 모델이나 필요한 설치가 없으면 함수 시험을 먼저 완료하고 엔진 gate는 미검증으로 남긴다. 모델 전체 의미 보존 성공으로 결론 내리지 않는다.

호출 직전·직후의 Python, NumPy, torch, CUDA RNG 상태와 관련 입력·출력 버퍼, cache 내용·소유자·길이, token IDs, 가능하면 logits를 기록한다. 관찰 때문에 전역 난수를 소비하지 않는다. off와 on의 할당 주소가 다르다는 이유만으로 의미 변화라고 세지 않는다. 기존 startup 탐침의 RNG 간섭 회귀를 포함한다.

## 필수 통과 조건과 비용

지원 범위의 유효 결함에서 오답 유출은 0이어야 한다. 정상 8개는 모두 정상 결과를 전달해야 하며, 잘못된 거부와 불필요한 수치 변경도 0이어야 한다. 필수 경계 누락과 검사 실패는 허가를 발급하지 않아야 한다. 항상 차단해서 안전성 수치만 높이는 구현은 정상 사용 gate에 실패한다.

참조 경로를 사용한 정상 결과는 사전에 선언한 수치 계약으로 판정한다. off와의 작은 비트 차이 자체를 실패로 세지 않되, 차이와 허용치를 원자료에 남긴다. 원래 커널을 그대로 사용하는 정상 호출은 출력 보존도 확인한다. 허용치를 넘는 차이, RNG·cache 의미의 변화, 잘못된 교정은 비간섭 실패다.

교정 수와 차단 수를 따로 보고하고, 알려진 타일 오류 개발 사례는 실제 교정 전달을 입증해야 한다. holdout의 합격은 유출 0과 정상 사용 조건으로 정하고 교정 비중도 공개한다. 그래프 지원, 함수 단위 성과, 실엔진 성과, 새 GPU 재검증은 별도 항목이다.

scheduled, reached, mutation_effective, normal_delivered, repaired_delivered, blocked, wrong_escaped, unknown, error를 모든 시나리오에서 집계한다. 전체 계획 대비 검증 완료 수와 유효 결함 대비 교정·차단 수를 함께 낸다. 누락은 분모에 남기고 pass로 처리하지 않는다. 유한한 holdout 통과는 범용 무오류의 증명이 아니다.

시작, 첫 검증, 정상 반복, 교정·참조 반복 시간을 나눠 측정한다. 각 정상 반복 구간은 off/on 순서를 바꾼 5짝으로 측정하고 중앙값·범위·메모리를 보고한다. 전체 출력 검증의 비용을 현재 표본 점검의 약 1% 비용과 혼동하지 않는다. 비용 예산은 환경 조사 뒤 별도로 고정하며, 이를 맞추려고 검증 범위를 몰래 줄이지 않는다. 보존 시험과 실용성 예산의 합격을 따로 표시한다.

## 제출할 원자료

결과 폴더에는 freeze manifest와 hash, 코드 patch·commit, 설치 wheel hash와 환경 lock, 실행 명령·환경변수, 입력·전체 oracle·전체 반환 텐서, 호출·전달 관찰, RNG·cache·buffer 상태, entail JSONL, stdout·stderr·exit code, 시간 원표, 사례별 판정과 summary를 저장한다. 큰 파일은 별도 묶음의 위치와 hash를 기록한다.

결과 집계기는 누락 또는 판정 불가가 있으면 전체 검증 완료를 반환하지 않는다. failed, incomplete, passed를 구분한다. 결과를 본 뒤 수정한 코드는 회고 수리로 따로 기록하고 원래 holdout 결과를 덮지 않는다.

한 GPU에서 완료한 동일한 wheel·harness를 다른 GPU architecture나 driver에서 재검증할 때는 새 환경 fingerprint와 그 환경의 freeze manifest를 발급한다. 기존 환경의 성공을 그대로 승계하지 않는다.
